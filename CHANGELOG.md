# Changelog

## [Unreleased]

### Added

- Initial release: `Scry.Engine.Exqlite` -- a real, kind-independent `Scry.Core.EngineBehaviour` implementation over SQLite via `exqlite`'s own low-level `Exqlite.Sqlite3` API. `fetch/2` streams a full table in batches via `Exqlite.Sqlite3.multi_step/3` (2,000 rows/NIF call by default, `config :scry_engine_exqlite, chunk_size: n` to override) rather than one-row-per-NIF-call `step/2`. `fetch/3` additionally runs `query.wheres` through `Scry.Engine.Exqlite.WhereTranslator` and appends whatever real SQL `WHERE` clause it can build (bound `?` parameters, never string-interpolated values), falling back to `fetch/2`'s own unfiltered scan for anything it can't translate.
- `Scry.Engine.Exqlite.Conn` -- wraps an already-open `Exqlite.Sqlite3.db()` connection (`open/2`, `close/1`), meant to be opened once and reused across many `fetch` calls rather than reopened per call.
- `Scry.Engine.Exqlite.WhereTranslator` -- translates top-level `{:cmp, op, [field], value}` predicates (and the leaves of a top-level `{:and, ...}` chain among them) into SQL, for every comparison operator but `:match`, only when `field` is a single-segment, SQL-identifier-safe path and `value` is a plain string/integer/float. `nil`, booleans, `{:field, ...}`, and `{:param, ...}` right-hand sides are deliberately never translated, to avoid the one direction (silently dropping a row a correct fetch would have returned) `Scry.Core.Executor`'s own re-verification can never catch.
- Table and field names are validated against a plain SQL-identifier pattern before ever being interpolated into a SQL string -- both are query-supplied values, treated as untrusted input.

- `Scry.Engine.Exqlite` now also implements the new, optional `Scry.Core.EngineBehaviour.fetch/4` -- `Scry.Core.Executor` prefers it automatically over `fetch/3`/`fetch/2` for every query. `opts.columns` (`Scry.Core.Executor.referenced_top_level_fields/2`'s own static analysis of what a query actually references) becomes `SELECT <columns> FROM table` instead of always `SELECT *` when it's `{:ok, columns}`, falling back to `SELECT *` for `:unknown` -- byte-identical to today's behavior. Either way, rows come back as `Scry.Core.Row` (a shared column-index map built once per fetch, paired with each row's own positional values tuple) instead of a brand-new `Map.new/1` per row -- the other real, measured cost of a `GROUP BY`/`WHERE` scan over a large table needing only a few of its many columns. Column names are validated against the exact same SQL-identifier pattern `source` already is, before ever reaching a SQL string.

- `Scry.Engine.Exqlite` now also implements the new, optional `Scry.Core.EngineBehaviour.aggregate/5` -- real, native `GROUP BY`/aggregate pushdown, preferred automatically by `Scry.Core.Executor` for any eligible query. Unlike `fetch/3`/`fetch/4`'s own lenient pushdown, this is authoritative: declines gracefully (`:not_supported`, `Scry.Core.Executor` falls back to computing it row-by-row) unless every `GROUP BY`/aggregated column is a safe SQL identifier, `WHERE` is *fully* translatable (`Scry.Engine.Exqlite.WhereTranslator.translate_strict/2`, new -- also resolves `{:param, name}` against `params`, which `translate/1` never does since `fetch/3` isn't handed `params` at all), and every aggregated column is schema-level `NOT NULL` (`PRAGMA table_info`, checked in the *same transaction* as the aggregate query itself -- closes a real TOCTOU gap where another connection's schema change between an isolated check and the query could let a `NULL` slip through undetected).
  The `NOT NULL` gate exists because SQL's own `SUM`/`COUNT(col)`/`MIN`/`MAX`/`COUNT(DISTINCT col)` all silently skip `NULL` values (confirmed empirically against a real SQLite database), where lang_spec §7 requires "aggregates over nullable fields hard-error -- no silent nil-skipping." `avg` is excluded from pushdown eligibility entirely -- SQLite's `AVG()` always returns an inexact float (also confirmed empirically), which would silently break lang_spec §4's "exact rationals by default" promise. A `NULL` result for `SUM`/`MIN`/`MAX` (only possible for a `group_bys == []` flat aggregate over zero matching rows -- SQL still returns exactly one row) is translated into `Scry.Core.Executor`'s own `:empty` sentinel before returning.
  This is the one place this package stops being fully schema-agnostic -- a deliberate, narrow, documented exception for this one capability, not a broader policy change.
  `test/scry/engine/exqlite/aggregate_test.exs`: `sum`/`count`/`min`/`max`/`count(distinct ...)` pushdown against a real SQLite database, a flat aggregate (including over zero matching rows), a `{:param, name}`-bound `WHERE`, the `NOT NULL` gate correctly declining for a nullable column while `Scry.Core.Executor`'s own fallback still produces the correct final result, an untranslatable `WHERE` predicate declining gracefully, and an unknown source still surfacing as a clear error through the full `Scry.Core.Executor.run/4` path. `test/scry/engine/exqlite/where_translator_test.exs` gains matching coverage for `translate_strict/2`.
