# Changelog

## [Unreleased]

### Fixed

- `SqlCompiler.order_by_item/2` now correctly accepts the `{:field, [column]}`-tagged sort-key shape `scry_core`'s EP1(e) `ORDER BY` widening (`ORDER BY <any expr()> ASC|DESC`, e.g. an upcoming `relevance()` call or `price * quantity`) produces for every real parsed query's own bare-field case -- `Scry.Core.Query.t()`'s own `order_bys` field is now `[{expr(), :asc | :desc}]` rather than `[{[String.t(), ...], :asc | :desc}]`, so a bare `ORDER BY name ASC` compiled from real query text arrived as `{:field, ["name"]}`, not `["name"]`, and fell through to this module's `:error` catch-all -- a real regression that would have rejected *every* pushdown-eligible `ORDER BY`, not just the new expression forms this module still correctly declines (a call, arithmetic, a multi-segment field). The older bare-list shape (`["name"]`, still built directly by some callers, e.g. a hand-constructed `%Query{}` in this package's own test suite) keeps working unchanged, alongside the new tagged shape -- this compiler still gains no general expression-compilation capability; anything else tagged still declines to `{:error, {:unsupported, {:order_by, ...}}}`, exactly as before.

### Added

- `Scry.Engine.Exqlite` implements `Scry.Core.EngineBehaviour`'s new optional `describe_source/2` callback -- feeds `Scry.Core.TypeCheck.Introspection` (`scry_core`'s own compile-time type system) a real source's own `PRAGMA table_info`-derived schema whenever a query doesn't declare an inline `TYPE` for it. New `Scry.Engine.Exqlite.Schema`: the engine's existing private schema-introspection internals (`fetch_table_info/2`, `cached_table_info/3`, `schema_version/1`, `verify_schema/3`, `column_guaranteed_not_null?/2`, `column_affinity/1`) extracted and made public, byte-for-byte identical behavior -- `execute/3`'s own per-query, transaction-scoped `NOT NULL`/type-affinity gate is untouched, just now calling `Schema.verify/4` instead of an inline private function, and routes through the exact same per-`Conn` ETS cache `describe_source/2` also uses. `Schema`'s own `introspected_scalar/1` is a deliberately honest translation of SQLite's 5-rule type affinity into `:integer`/`:float`/`:string`/`:unknown` -- distinguishes `:integer` from `:float` where SQLite's own rules genuinely do (an `INT`- vs `REAL`/`FLOA`/`DOUB`-containing declared type), but reports `:unknown` rather than guessing for `BLOB`/no declared type and the default `NUMERIC`-affinity catch-all, which SQLite itself can't pin down from declared-type text alone.
  `test/scry/engine/exqlite/schema_test.exs`; `test/scry/engine/exqlite_test.exs` gains a small `describe_source/2` describe block confirming the engine-level delegation, and its existing schema-gate tests pass unmodified, confirming the refactor didn't change `execute/3`'s own behavior.

### Changed

- **Breaking**: `execute/3`'s own direct (non-delegated) pushdown path now returns `Scry.Core.Row.t()` values instead of plain maps -- building a brand-new string-keyed map for every single row is real, measured cost at scale (a caller counting/paginating/streaming a handful of fields never needed the other columns' own hashing at all); `Scry.Core.Row`'s own moduledoc has the full reasoning, and it's already a first-class row shape throughout `Scry.Core.QueryOps`. A nested/correlated `SELECT` or `WITH`-bound source still returns plain maps -- delegated whole to `Scry.Core.QueryOps.run_document/4`, whose own final projection step always builds one regardless of what shape any recursively-invoked engine returned internally. A caller wanting a plain map calls `Scry.Core.Row.to_map/1`; `Row.fetch!/2` reads a single field without ever materializing the rest.
- The schema check itself (`NOT NULL`/type-affinity verification) is now cached per `Scry.Engine.Exqlite.Conn`, keyed by table, invalidated via SQLite's own `PRAGMA schema_version` (a single cheap integer read, bumped by any schema-altering statement against the database file from any connection) rather than trusted indefinitely -- a real, measured cost for a small query, where the check's own `PRAGMA table_info` round trip dwarfed the actual query. `Scry.Engine.Exqlite.Conn.open/2` now also creates the ETS table backing this cache, cleaned up by `close/1`; a `%Conn{db: db}` built by hand (common in tests) simply has no cache and re-checks every call, same as before -- always correct, just not optimized.
- **Found by property testing while validating the above, not assumed**: SQLite's own type-affinity-coercion rule applies to *every* comparison operator, not just the ordering ones `SqlCompiler`'s own type-affinity check already covered -- an `INTEGER`-affinity column genuinely `= "2"` (the string literal) in SQLite, where the interpreter's own `=` never considers a string and a number equal. `type_checks` collection is no longer scoped to `:lt`/`:gt`/`:le`/`:ge`; `=`/`!=`/`IN` are checked identically now (a mixed-type `IN` list against one field collects more than one required class for that column, which can never simultaneously hold, so it declines safely rather than trust whichever type happens to match). `SqlCompiler`'s own moduledoc previously stated `=`/`!=` were safe from this -- that was an unverified assumption, now corrected.
- The schema-checked (eager) path's own `fetch_all` call now passes this module's own configured chunk size explicitly, instead of implicitly taking `exqlite`'s own default (50 rows/NIF call) -- found reasoning through `exqlite`'s own source after the two fixes above alone barely moved a large (1,000,000-row) `GROUP BY`'s own duration: 50 rows/call means 20,000 NIF round trips for a result that size, 40x more than the 2,000-row chunking the plain streamed path (and this package's own benchmark's raw-SQL comparison) already used. Re-measured via `scry_test_core`'s own `mix scry.bench --users 1000000`: the adversarial 1,000,000-group `GROUP BY user_id` case drops from ~1.94x-2.04x raw-SQL overhead to ~1.53x-1.56x; `avg`/low-cardinality `GROUP BY` stay at genuine parity (~1.0x-1.05x). A point lookup's own overhead (still ~8-10x, though both sides are sub-millisecond in absolute terms) is now dominated by the fixed cost of the schema-check transaction itself (`BEGIN`/`PRAGMA schema_version`/`COMMIT`, ~6 extra SQLite calls even on a cache hit) rather than by chunking or per-row allocation -- a real, remaining, architectural floor this increment doesn't attempt to close further.

- **Breaking**: `Scry.Engine.Exqlite` implements `Scry.Core.EngineBehaviour`'s new single authoritative `execute/3` callback instead of `fetch/2,3,4`/`aggregate/5` -- the old contract is gone from `scry_core` entirely (its own `CHANGELOG.md` has the full reasoning). `execute/3` compiles the *entire* flat query -- `WHERE`/`GROUP BY`/aggregates/`ORDER BY`/`DISTINCT`/`LIMIT`/`OFFSET`/projection -- into one native SQL statement via the new `Scry.Engine.Exqlite.SqlCompiler`, all or nothing, with **no fallback**: a query shape it can't fully translate is a clean `{:error, {:unsupported, detail}}`, never a partial pushdown silently finished off in Elixir. `Scry.Engine.Exqlite.WhereTranslator` is rewritten from a lenient, top-level-`:and`-only translator into a single `translate/2` that fully and recursively translates `{:cmp,...}`/`{:in,...}`/`{:and,...}`/`{:or,...}`/`{:not,...}` trees, correctly special-casing SQL's own `field = NULL`/`field != NULL` semantics (always `IS NULL`/`IS NOT NULL`, never a bound `= ?`/`!= ?`).
  `avg` is now pushdown-eligible, returning a native (inexact) SQL float -- `scry_core`'s own `CHANGELOG.md` has the full reasoning for relaxing the "exact rational arithmetic regardless of backend" guarantee to a per-engine capability. Relaxing exactness never meant relaxing null-safety: every aggregated column (including `avg`'s own target column) and every column compared against a non-`nil` `WHERE` literal must still be schema-level `NOT NULL` (`PRAGMA table_info`, checked in the same transaction as the compiled query), an `INTEGER PRIMARY KEY`/`ROWID`-alias column counting as guaranteed-not-null despite reporting `notnull: 0` in its own schema row (confirmed directly against real `PRAGMA table_info` output, not assumed).
  A second, previously-latent correctness subtlety was found by property testing (`test/scry/engine/exqlite/sql_compiler_property_test.exs`), not assumed: SQLite's own type-affinity-based comparison rules can disagree with this project's Erlang-term-order comparison semantics for `<`/`>`/`<=`/`>=` when a column's declared type doesn't match the compared literal's type (e.g. a `TEXT` column compared against an integer literal) -- `SqlCompiler` now also collects the real SQLite type affinity every ordering comparison implies, checked against each column's actual declared type (the same 5-rule algorithm SQLite itself documents) in the same schema-check transaction, declining with `{:error, {:unsupported, {:type_mismatch, checks}}}` rather than risk a silently wrong ordering result.
  A nested/correlated `SELECT` body item or a `WITH`-bound source is delegated whole to `Scry.Core.QueryOps.run_document/4`, recursing back into this same module's `execute/3` for each flat leaf it resolves.
  `HAVING`, `ROLLUP`/`CUBE`, window functions, and any non-bare-field `select` item (casts, arithmetic) are explicitly out of scope for this increment and decline cleanly rather than attempting a fragile partial translation.

### Fixed

- `SqlCompiler` now accepts a bare field under an explicit alias (`{:computed, alias, {:field, [column]}}`) as a plain `select` item or a `GROUP BY`-matching column, not just an unaliased `{:field, [column]}` -- found auditing `scry_test_core`'s own cross-engine parity suite: `Scry.Core.Query.from/2`'s map-shaped `select:` always wraps every entry this way, even a plain field reference, so a query built through the native Layer 2 front end was declining pushdown it should have gotten.

### Added

- `WhereTranslator` now translates a `DateTime.t()`/`NaiveDateTime.t()` `WHERE` literal (e.g. lang_spec.md's own `DATE` token, or a kind package's own generated predicate like `scry_time_series`'s `LAST`) instead of declining the whole query outright -- bound as its own Unix epoch (microseconds) integer, the one concrete on-the-wire representation this module picks since SQLite has no native timestamp type of its own. The compared column must itself be stored the same way, or `SqlCompiler`'s own type-affinity check (the same `:numeric` class a plain integer/float literal gets) correctly declines the comparison rather than risk silently comparing an epoch integer against, say, an ISO 8601 string column. Found validating `scry_test_time_series` against this repo's new `execute/3` contract -- a `DateTime` literal previously had no translation at all, so any SQLite-backed time-series `LAST` query declined outright.

- Initial release: `Scry.Engine.Exqlite` -- a real, kind-independent `Scry.Core.EngineBehaviour` implementation over SQLite via `exqlite`'s own low-level `Exqlite.Sqlite3` API. `fetch/2` streams a full table in batches via `Exqlite.Sqlite3.multi_step/3` (2,000 rows/NIF call by default, `config :scry_engine_exqlite, chunk_size: n` to override) rather than one-row-per-NIF-call `step/2`. `fetch/3` additionally runs `query.wheres` through `Scry.Engine.Exqlite.WhereTranslator` and appends whatever real SQL `WHERE` clause it can build (bound `?` parameters, never string-interpolated values), falling back to `fetch/2`'s own unfiltered scan for anything it can't translate.
- `Scry.Engine.Exqlite.Conn` -- wraps an already-open `Exqlite.Sqlite3.db()` connection (`open/2`, `close/1`), meant to be opened once and reused across many `fetch` calls rather than reopened per call.
- `Scry.Engine.Exqlite.WhereTranslator` -- translates top-level `{:cmp, op, [field], value}` predicates (and the leaves of a top-level `{:and, ...}` chain among them) into SQL, for every comparison operator but `:match`, only when `field` is a single-segment, SQL-identifier-safe path and `value` is a plain string/integer/float. `nil`, booleans, `{:field, ...}`, and `{:param, ...}` right-hand sides are deliberately never translated, to avoid the one direction (silently dropping a row a correct fetch would have returned) `Scry.Core.Executor`'s own re-verification can never catch.
- Table and field names are validated against a plain SQL-identifier pattern before ever being interpolated into a SQL string -- both are query-supplied values, treated as untrusted input.

- `Scry.Engine.Exqlite` now also implements the new, optional `Scry.Core.EngineBehaviour.fetch/4` -- `Scry.Core.Executor` prefers it automatically over `fetch/3`/`fetch/2` for every query. `opts.columns` (`Scry.Core.Executor.referenced_top_level_fields/2`'s own static analysis of what a query actually references) becomes `SELECT <columns> FROM table` instead of always `SELECT *` when it's `{:ok, columns}`, falling back to `SELECT *` for `:unknown` -- byte-identical to today's behavior. Either way, rows come back as `Scry.Core.Row` (a shared column-index map built once per fetch, paired with each row's own positional values tuple) instead of a brand-new `Map.new/1` per row -- the other real, measured cost of a `GROUP BY`/`WHERE` scan over a large table needing only a few of its many columns. Column names are validated against the exact same SQL-identifier pattern `source` already is, before ever reaching a SQL string.

- `Scry.Engine.Exqlite` now also implements the new, optional `Scry.Core.EngineBehaviour.aggregate/5` -- real, native `GROUP BY`/aggregate pushdown, preferred automatically by `Scry.Core.Executor` for any eligible query. Unlike `fetch/3`/`fetch/4`'s own lenient pushdown, this is authoritative: declines gracefully (`:not_supported`, `Scry.Core.Executor` falls back to computing it row-by-row) unless every `GROUP BY`/aggregated column is a safe SQL identifier, `WHERE` is *fully* translatable (`Scry.Engine.Exqlite.WhereTranslator.translate_strict/2`, new -- also resolves `{:param, name}` against `params`, which `translate/1` never does since `fetch/3` isn't handed `params` at all), and every aggregated column is schema-level `NOT NULL` (`PRAGMA table_info`, checked in the *same transaction* as the aggregate query itself -- closes a real TOCTOU gap where another connection's schema change between an isolated check and the query could let a `NULL` slip through undetected).
  The `NOT NULL` gate exists because SQL's own `SUM`/`COUNT(col)`/`MIN`/`MAX`/`COUNT(DISTINCT col)` all silently skip `NULL` values (confirmed empirically against a real SQLite database), where lang_spec §7 requires "aggregates over nullable fields hard-error -- no silent nil-skipping." `avg` is excluded from pushdown eligibility entirely -- SQLite's `AVG()` always returns an inexact float (also confirmed empirically), which would silently break lang_spec §4's "exact rationals by default" promise. A `NULL` result for `SUM`/`MIN`/`MAX` (only possible for a `group_bys == []` flat aggregate over zero matching rows -- SQL still returns exactly one row) is translated into `Scry.Core.Executor`'s own `:empty` sentinel before returning.
  This is the one place this package stops being fully schema-agnostic -- a deliberate, narrow, documented exception for this one capability, not a broader policy change.
  `test/scry/engine/exqlite/aggregate_test.exs`: `sum`/`count`/`min`/`max`/`count(distinct ...)` pushdown against a real SQLite database, a flat aggregate (including over zero matching rows), a `{:param, name}`-bound `WHERE`, the `NOT NULL` gate correctly declining for a nullable column while `Scry.Core.Executor`'s own fallback still produces the correct final result, an untranslatable `WHERE` predicate declining gracefully, and an unknown source still surfacing as a clear error through the full `Scry.Core.Executor.run/4` path. `test/scry/engine/exqlite/where_translator_test.exs` gains matching coverage for `translate_strict/2`.
